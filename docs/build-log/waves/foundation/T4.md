## Endpoints (`src/domains/auth/`)

`POST /auth/login` (public) · `POST /auth/refresh` (public) · `POST /auth/logout` ·
`GET /auth/me` · `PATCH /auth/me` · `POST /auth/me/password` — bodies, returns and error codes as in
the contract table. POSTs answer 200.

- **Access token**: HS256 JWT, 15 min, `{ sub, roleId, permissions[], sid }`. `sid` is the session
  (refresh-token family id) so "revokes other sessions" can keep the caller's own.
- **Refresh token**: 256-bit random, base64url; stored as SHA-256 in `RefreshToken.tokenHash`;
  30 days from each issue. One family per sign-in. Rules (`auth.pure.ts` → `decideRefresh`):
  unknown / revoked / expired → 401 `INVALID_REFRESH`; first use → marked used (atomic
  `updateMany … usedAt: null`), next token linked via `replacedById`; used ≤ 30 s ago → another pair
  in the same family (two tabs); used > 30 s ago → the whole family is revoked, 401. The revoke runs
  after the transaction so the 401 doesn't roll it back. A deactivated user's refresh also revokes.
- **Per-request check**: `JwtStrategy` checks the user exists and is active on every request
  (one `select active` by id) → 401 `UNAUTHORIZED`. **The permissions guard trusts the token's
  `roleId` and `permissions`** (≤ 15 min old, which the contract allows); `GET /auth/me` reads them
  live from the role.
- **Rate limit**: DB-backed (`login_attempts`, new migration `20261022183937_login_attempts`). Each
  failure (unknown email, wrong password, deactivated) inserts a row; once 10 failures for the
  normalised email are newer than 15 min, the next attempt is 429 `TOO_MANY_REQUESTS` before any
  check. A success clears that email's rows; each failure deletes rows older than the window.
- Identical 401 `INVALID_CREDENTIALS` body for all three failures; an unknown email still runs a
  scrypt verify against a decoy hash so timing doesn't tell.
- `PATCH /auth/me`: name (trimmed, 1–100), phone (as typed → E.164; `null` clears), language.
  Anything else → 400 (strict pipe). `POST /auth/me/password`: wrong current → 400
  `WRONG_PASSWORD`; new 8–128 chars; hash + revoke other sessions in one transaction.
- `POST /auth/logout` revokes the presented token's family when it belongs to the caller;
  anything else is a silent no-op (`null`).

## Edge cases → tests

Each plan case is an `it` with its name in `test/auth.e2e-spec.ts`; most also have a unit test
(`auth.pure.spec.ts`, `session.service.spec.ts`, `auth.service.spec.ts`, `jwt.strategy.spec.ts`).

- Correct email + password → tokens and Me with permissions
- Wrong password, unknown email, deactivated user → identical 401 INVALID_CREDENTIALS
- Email matched case-insensitively and trimmed
- 11th failed attempt within 15 min → 429 (and: per email, other emails unaffected, unlocks when
  the oldest failure leaves the window; a success resets the count)
- Refresh rotates: old token reused after the grace window → 401 and the whole family revoked
- Two refreshes with the same token within 30 s → both succeed (truly concurrent, plus one at
  exactly 30 s; every pair keeps working, one family)
- Deactivated user's valid access token → 401 on next request
- Password reset by admin revokes all refresh tokens (revokeAllSessions; bystander unaffected;
  rolls back with its transaction)
- Change password with wrong current → 400 WRONG_PASSWORD; new < 8 chars → 400
- PATCH /auth/me cannot change role, email or active
- Generic: missing / extra / wrong-type fields → 400 on every body; no token, expired token,
  forged signature → 401; Arabic + emoji name in `PATCH /me` (trimmed); invalid phone, empty
  name, unknown language → 400; expired (30-day) refresh → 401; logout of another user's token is
  a no-op; changed password signs in, the old one doesn't, other sessions end, the current stays.

## Decisions and deviations

- **Added a `LoginAttempt` table** (plan had no schema change for T4): DB-backed so the limit
  holds across Vercel function instances. Template refreshed after the migration.
- **`sid` claim added to the access token** (not in the contract's claim list) so
  `POST /auth/me/password` can keep the current session while revoking the others. Tokens without
  it (test fixtures) revoke all sessions.
- **Guard trusts token permissions; only `active` is checked live.** Live permissions would cost a
  role join per request and break T3's fixture tokens; the contract's "next access token" wording
  allows ≤ 15 min staleness.
- **Rate limit counts failures, not attempts**; a success clears the count. Two failures racing
  past the 10th can both be recorded (count-then-insert isn't atomic) — at worst an 11th/12th 401
  before the 429; acceptable for this threat model.
- **Logout does not invalidate the access token** (stateless JWT, ≤ 15 min); the web discards it.
- Self-service profile and password changes are not written to the activity log (the business doc
  lists admin user changes only).
- `docs/BUSINESS_LOGIC.md`: added the sign-in/session rules paragraph.
