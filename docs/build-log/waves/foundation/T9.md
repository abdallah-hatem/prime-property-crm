## Timing (20 000 owners, local Postgres 17 in Docker, Windows laptop)

xlsx of 20 000 rows (~390 KB): upload 2.5–3.0 s · preview 0.3–0.5 s · confirm 5.8–7.9 s
(normal pool and `VERCEL=1`). The test fails if confirm takes 55 s or more. Inserts are
`createMany` in chunks of 1000 rows (owners, phones, notes, assignments), issue writes are one
`UPDATE … FROM unnest(…)` per 5000 rows, and duplicate lookups pass every phone as one array
parameter (`= ANY($1::text[])`), so no query is per row. Import transactions use a 55 s timeout
(`IMPORT_TX_OPTIONS`) instead of Prisma's 5 s.

## Endpoints

`POST /imports` (multipart `file`, `kind`) · `POST /imports/:id/preview` · `POST /imports/:id/confirm`
· `GET /imports` · `GET /imports/:id/issues`.

- Upload: the kind's permission first (`owners.import` / `listings.create`, else 403), then the
  file. Format is the extension checked against the content (zip → exceljs, OLE → SheetJS, text →
  csv-parse with BOM / UTF-16 / `,` `;` tab detection). Every cell becomes text (whole numbers
  without exponent). First non-blank row = header (empty → `Column N`, repeated → `Name (2)`),
  blank rows skipped but row numbers kept (1 = the first row under the header). Rows go to
  `import_rows.data` as string arrays. `mapping` in the response is the suggestion from the
  header names (EN/AR, Arabic letter variants folded). Multer's 413 is mapped to
  `400 FILE_TOO_LARGE`. An Arabic file name survives (multer's Latin-1 read is undone).
- Preview: creator only (anyone else 404), status not DONE (`409 IMPORT_NOT_EDITABLE`), mapping
  keys must be fields of the kind and values headers of the file (`400 MAPPING_INVALID`), required
  fields mapped (`400 MAPPING_INCOMPLETE`). `assignTo` needs `owners.assign` (403) and an active
  user (`400 INVALID_ASSIGNEE`). Every row is checked, issues are stored per row, the job becomes
  PREVIEWED with `counts` = what confirm would do. Returns `{ job, sample (20), issues (100) }`.
  Preview can be repeated (re-mapping replaces the issues), also after a FAILED confirm.
- Confirm: creator only; locks the job row (`FOR UPDATE`), re-checks status, assignee and every row,
  inserts, writes one IMPORT activity entry (`details: { kind, counts, assignToId }`) and, when
  something was assigned, one ASSIGN entry. Any unexpected error rolls everything back, marks the
  job FAILED with the error text and answers `500 IMPORT_FAILED`; a 4xx (state, assignee) leaves
  the job as it was.
- Owners rows: `name`, `phone`, `phone2`, `phone3`, `area`, `note` (note → a Note by the importer).
  Status NEW, `sourceImportId` set, assigned to `assignTo` with one OwnerAssignment row each.
- Listings rows: `name`, `phone` (owner contact) and the `POST /listings` fields; values are read
  (purpose/type/furnishing in EN or AR, numbers with separators or Arabic digits) and then
  validated with the same `CreateListingDto`. Member = `assignTo` or the importer. A phone of a
  live owner lead links the listing; the lead becomes LISTED and, when its member differs, moves
  through `AssignmentService.reassignOwnerAndListing` (reminders follow, one ASSIGN entry).
- Duplicates: any phone of the row held by an owner (any slot, trashed included → `inTrash`), a
  live listing, or an earlier row that will be added. Listings: also an owner lead that already
  has a live listing (matches that listing) or that an earlier row already links.
- Issues: `matches.ownerId` only for `owners.viewAll` (a trashed owner's only for `trash.restore`),
  like `409 PHONE_EXISTS`; listing ids are always shown. `GET /imports/:id/issues` is for the
  creator or `owners.import`, filter `reason`, paginated. `GET /imports` lists only the kinds the
  caller may import (asking for another kind → 403).

## Decisions and deviations from the plan

- **Listings also require `sizeSqm`**: the spec lists purpose, type, area, price, but `POST /listings`
  and the NOT NULL column need size too.
- **Issue reason for an empty phone cell is MISSING_REQUIRED**; a phone that doesn't parse is
  INVALID_PHONE (both rejected). An invalid `phone2`/`phone3` rejects the row too.
- **A FAILED import can be previewed and confirmed again** (the plan doesn't say). Only DONE is final.
- **`counts` is filled at preview** (what confirm would do) and replaced at confirm.
- **New codes** `MAPPING_INVALID` (400) and `IMPORT_FAILED` (500) besides the spec's list.
- Within-file duplicates have `matches: null` (no column to keep the earlier row number).
- Row numbers count data rows from 1 (the `ImportRow.rowNumber` comment), not sheet row numbers.
- The ASSIGN activity text is a third copy of the one in OwnersService/ListingsService; worth
  extracting into the assignment domain when those files are next touched.
- No schema change.
- New dependencies in `apps/api`: `exceljs` 4.4.0, `csv-parse` 6.1.0, `xlsx` 0.20.3 (SheetJS, from
  its official CDN tarball), `@types/multer` (dev).
- `docs/BUSINESS_LOGIC.md`: new paragraph "Imports (built, T9)".
