## What changed

- **Race.** `UserStatusService.deactivate` calls `UserStatusRepository.lockUser(tx, id)`
  (`SELECT id FROM users WHERE id = $1 FOR NO KEY UPDATE`) first in its transaction, before
  reading the user or their work. `UserDirectoryRepository.findActive(id, tx)` now reads
  `SELECT id, name FROM users WHERE id = $1 AND active = true FOR SHARE` when given a `tx`
  (unchanged without one). `AssignmentService.assertAssignee` goes through it, so an assignment
  holds the assignee's row until it commits: deactivation waits and then hands that work over,
  or the assignment waits and finds the member inactive (400 INVALID_ASSIGNEE).
- **Helper.** `src/domains/assignment/assign-activity.ts` — `assignActivity(actorId, { kind,
  count, assignee, linkedOwners? })` returns the ASSIGN `ActivityRecordInput` (summary, USER
  target, `details: { kind, count, assigneeId }` plus `linkedOwners` when > 0). Used by owners
  create/assign, listings assign, the direct-listing lead move, and owners/listings imports. The
  three private `recordAssign` copies are gone.
- **Listings import with `assignTo`**: one ASSIGN entry `{ kind: 'LISTINGS', count: <listings
  added>, assigneeId, linkedOwners? }`, linked or not. Without `assignTo` the listings are the
  importer's own; leads that moved to the importer still get one OWNERS entry, as before.
- `docs/BUSINESS_LOGIC.md`: the import assignment entry and the race rule under the invariants.
  Plan: both T10b cases ticked.

## Decisions and deviations

- **`FOR NO KEY UPDATE`, not `FOR UPDATE`, on the user row.** It still conflicts with the
  assignment's `FOR SHARE`, but not with the `FOR KEY SHARE` a foreign-key check takes. With `FOR
  UPDATE`, two admins deactivating each other would deadlock (each tx's activity insert naming its
  actor waits on the other's row lock while the other waits on the Admin role lock). Same choice
  as `UserRepository.lockAdminRole`.
- The existing flow-5 import test asserted an ASSIGN entry with `count: 1` (the moved lead). It
  now expects the single batch entry `{ kind: 'LISTINGS', count: 2, linkedOwners: 1 }`. The import
  tests find new entries by id (not by `createdAt`, which could skew against the DB clock).
- Every existing caller of `assertAssignee` takes it before locking any owner/listing row, so the
  new `FOR SHARE` adds no lock-order cycle with the deactivation (user row, then work).

## Follow-ups

- `POST /listings` (direct, no `assignedTo`) gives the listing and a linked lead to the creator,
  and only reads the creator (`findActive`) after the writes. If the creator is deactivated while
  that request is in flight, the records can end up on them and the entry reads "Unassigned".
  Rare (a user deactivated mid-request); checking the creator with `assertAssignee` before the
  writes would close it.
- Web (T15/T16): ASSIGN `details.linkedOwners` is new and optional.
