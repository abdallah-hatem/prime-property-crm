## Shared pieces later domains must use

Permissions and the caller
- `src/common/decorators/require-permission.decorator.ts`: `@RequirePermission(...keys)`. The
  caller needs every listed key (typed `Permission` from `packages/shared`). Use it on a class or a method.
- `src/common/guards/permissions.guard.ts`: global `APP_GUARD`, registered after `JwtAuthGuard`.
  Answers 403 `FORBIDDEN`. Sets `isAdmin` by comparing the token's `roleId` with the built-in Admin
  role id (`AdminRoleService`, looked up by `Role.builtIn` and cached). Admin passes every check,
  including keys added after the token was issued.
- `src/common/decorators/get-user.decorator.ts`: `@GetUser()` / `@GetUser('id')` gives you a
  `CurrentUser { id, roleId, permissions, isAdmin }` (`common/interfaces/current-user.interface.ts`).
- `src/common/utils/permissions.util.ts`: `hasPermission(user, key)`, `hasAllPermissions`.
  Use these in services for "own or permission" branches. Never compare role names.

Ownership (not yours = 404)
- `src/common/utils/ownership.util.ts`: `ownerScope(user, 'assignedToId', { bypass: 'owners.viewAll' })`
  gives a `where` fragment you merge into a repository query. `assertAccessible(record, user,
  ownerOf, { bypass, what })`, `assertFound(record, what)` and `notFound(what)` all throw the
  same coded 404.

Soft delete and trash
- `src/common/repositories/soft-delete.repository.ts`: owners, listings and photos repositories
  extend `SoftDeleteRepository` with `super(db, (client) => client.owner)`. Every default query
  (findById, findFirst, count, findAllWithPagination, update) sees live rows only. These methods
  take an optional `tx`. `delete` refuses on purpose. `liveWhere()` / `LIVE` cover custom queries.
- `src/domains/trash/` (`TrashModule` exports `TrashService` and `TrashRestoreRegistry`):
  - `trash.softDelete(tx, kind, id, actorId)`: call it inside the domain's transaction, after the
    domain has checked access. It sets `deletedAt`/`deletedById`, logs `DELETE` and returns
    `{ label, deletedAt, purgeAt }`.
  - `registry.register(kind, { validate?, afterRestore? })` from the domain module's
    `onModuleInit`. `validate` throws the domain 409s (`OWNER_ALREADY_LISTED`,
    `PARENT_DELETED`, `TOO_MANY_PHOTOS`). `afterRestore` handles side effects, such as re-flagging the
    owner `LISTED`. Both run inside the restore transaction. The core already handles 404, 410 `PURGED`
    and 403, clears `deletedAt` and logs `RESTORE`.
- `src/common/utils/trash.util.ts`: `purgeAtFor`, `isRestorable` (inclusive at exactly 30 days)
  and `trashCutoff(now)`. The purge cron (T11) must remove `deletedAt < trashCutoff(now)` so it agrees
  with the trash list.
- `packages/shared/src/contract/trash.ts`: `TrashKind`, `TRASH_RETENTION_DAYS`, `TrashErrorCode`.

Activity log
- `src/domains/activity/` (`ActivityModule` exports `ActivityService`):
  `activity.record(tx, { type, actorId, summary, target?: { kind, id, label }, details? })`.
  Always pass the transaction of the change being logged.
- `GET /api/activity` (`activity.view`): `type` (repeat or comma list), `actorId`, `from`/`to`
  (a Cairo date `YYYY-MM-DD` or an ISO instant; a date `to` includes that whole day), `page`, `limit`.

## Edge cases → tests

Each plan case is an `it` with its exact name. Unit tests cover the guard, ownership,
trash.util and TrashService. E2e tests cover the real endpoints, plus a test-only probe controller with
one route per permission key.
- Endpoint with `@RequirePermission('x')` and a user without x → 403 (unit + e2e)
- Admin role always passes every permission check, even a permission added to the list later (unit + e2e)
- Ownership helper: member asking for someone else's record → NotFound, not Forbidden (unit + e2e)
- Activity writer inside a transaction rolls back with it (e2e; soft delete rollback too)
- Soft-deleted rows excluded from every default query (unit with an in-memory delegate + e2e on the real DB)
- Trash core computes purgeAt = deletedAt + 30 days (unit + e2e)
- Restore after purgeAt → 410 PURGED (unit + e2e; a row already purged by the cron also gets 410)
- Custom role with only owners.assign passes that check and is refused every other permission (unit + e2e)
- Item deleted exactly 30 days ago is still restorable; 30 days + 1 minute is not (unit + e2e, frozen Clock)
- Restore an item that isn't in the trash → 404; member calls restore → 403 (e2e)
- Generic checklist for `/activity` and `/trash`: no token, expired token and forged token → 401.
  Bad input → 400: page 0 or −1, limit 0, 21 or `abc`, fractional page, an unknown type, an unknown
  kind, a non-UUID actorId or id, a malformed date, Feb 30, an ISO week, from > to, an unknown query
  parameter. A page past the end comes back empty, and limit 1 sets `hasNextPage`.

## Decisions and deviations from the plan

- **The test database is `prime_crm_t3_test`, not `prime_crm_t3`.** The harness (`test/setup-env.ts`)
  refuses any database whose name doesn't end in `_test`.
- **Deadlock caught by the one-connection pool.** `restore` checked the activity log through the
  app client while the transaction held the only connection. It now reads through `tx`. Rule for
  every domain: inside `DatabaseService.transaction`, every read and write goes through `tx`.
  Run e2e with `VERCEL=1` once per backend task to catch this.
- **Soft delete logs `DELETE` itself.** The business doc says every deletion goes in the log, so
  domains don't each write it. Restore logs `RESTORE` the same way.
- **Restore dispatcher uses hooks, not full handlers.** The core always does the generic restore, so a
  kind with no registered handler (all of them until T6/T8) still restores correctly.
- **Purged vs never existed.** When the row is gone but the log has a `DELETE` for it, the answer is
  410 `PURGED`. Otherwise it's 404.
- **`GET /trash` with no `kind`** lists every kind together, newest deletion first (UNION for
  paging, then per-kind hydration).
- **Trash labels** are English snapshots: owner name; listing "Type · N BR · area"; photo
  "Photo n · listing". T8 owns the localized listing title and may swap `listingLabel`.
- `kind` in the trash routes is case-insensitive (`owner` or `OWNER`).
- `@RequirePermission` with several keys means **all** of them.
- `JwtStrategy` (auth domain) is untouched. T4 adds the "user still active" check there.
  `PermissionsGuard` builds `CurrentUser` from whatever the strategy attaches.
