## Decisions and deviations

- **Deactivating an already deactivated user returns it unchanged** (no hand-over, no entry);
  **reactivating an active user** likewise. The spec lists no error for either.
- **Check order**: self (400) and `handOverTo === id` (400) before the transaction; then 404,
  then last admin (409), then the recipient (400). The recipient is read after the Admin role
  lock, so it can't be deactivated concurrently by another deactivation.
- **Concurrent mutual deactivation**: the loser gets 409 `LAST_ADMIN`, or 401 when the winner
  committed before the loser's request passed the JWT active check. Both leave one admin.
- **Trashed owners/listings of the deactivated user are not moved**; the T6 owner restore
  handler brings them back unassigned when the member is inactive.
- The recipient can be any active user (including an admin), as with `assertAssignee`.
- `PATCH /settings` requires `adCheckInDays` (it is the only field).
- Business doc gained "Deactivation and reactivation (built, T10)" and "Settings (built, T10)".
