## Screens (all replace T12's placeholders; nav and the proxy already gate them by permission)

- `/users` (users.manage): search (name, email, mobile), role select and Everyone / Active /
  Deactivated pills, all in the URL with `scroll: false`; DataList (table from md, cards on
  phones; mobile column from lg). A row opens the user sheet: role, status, mobile, language,
  added date, what they hold now (owners, listings, open reminders), Edit details, Reset password,
  Deactivate / Reactivate. Deactivate is disabled with the reason for the last active admin
  (`GET /users?roleId=<Admin>&active=true` count ≤ 1) and for yourself; the edit form locks the
  role of the last active admin with the reason.
  - Create / edit: name, email, mobile (shared PhoneInput: 11 digits starting 01), role, language,
    initial password (create). EMAIL_TAKEN on the email field, LAST_ADMIN / INVALID_ROLE on the role.
  - Deactivate: loads the counts that will move and the active users; the hand-over is a required
    choice (another user + picker, or nobody), never pre-selected; the user being deactivated is
    not offered.
- `/roles` (roles.manage): role cards with user count, permission count and the first permissions;
  the editor groups the fixed list (people, owners, listings, reports, settings & trash) with EN/AR
  labels from `PERMISSIONS`. Admin: every box ticked and locked with the reason, its list is never
  sent. Delete is disabled with the reason for built-in roles and roles someone holds (ROLE_IN_USE
  translated too).
- `/settings` (settings.manage): check-in interval (1–90, Arabic digits read, explanation,
  "unchanged" note) and the call-outcome manager: add, edit EN/AR names and the status mapping
  (Listed never offered), hide / show, move up / down (writes `order` = position for each moved
  outcome), delete. An outcome in use opens "used in calls — hide it instead"; a delete refused
  with OUTCOME_IN_USE switches to the same offer.
- `/trash` (trash.restore): kind pills in the URL, item + kind, deleted by, deleted date with days
  left (amber in the last 3 days), Restore with a busy state. A refused restore keeps the item and
  says why on its row (OWNER_ALREADY_LISTED, PARENT_DELETED, TOO_MANY_PHOTOS, PURGED).
- `/activity` (activity.view): type select, Who select (active then deactivated users, only when
  the viewer may list users), Cairo date range (popover calendar, two taps), all in the URL.
  Entries read as sentences in the reader's language, built from type + target + details (falls
  back to the API's English sentence); a row opens its details (what moved, counts, role / name /
  permission changes, outcome field changes, restorable-until).
- Loading skeletons for each route (`loading.tsx`); every request has a skeleton, a dimmed list or
  a busy button.

## Decisions and deviations

- **The last-admin rule is drawn, not enforced, by the web**: the API still answers LAST_ADMIN
  (shown on the role field); the screen only explains before anyone tries.
- **Reorder** writes each moved outcome's `order` (two PATCHes for a swap; each logs an
  OUTCOME_UPDATE entry). There is no bulk reorder endpoint.
- **Initial / reset password fields are visible text** (the admin types it to hand it over).
- Permission labels come from the shared `PERMISSIONS` list, not `GET /roles/permissions` (same
  data, one request fewer).
- jsdom polyfills (ResizeObserver, pointer capture, scrollIntoView) live at the top of
  `admin.test.tsx` because `vitest.setup.ts` is shared.

## Contract gaps

- No shared zod schema for `TrashItem` and `ActivityEntry` (typed in the apis.ts block).
- `ActivityEntry.summary` is English only; the web rebuilds sentences from type/target/details.
  The sample seed's IMPORT (flat counts) and ASSIGN (`from`/`to` ids) details differ from what the
  API writes (`counts{…}`, `assigneeId`); listing target labels are English ("Apartment · 3 BR").
- No count of active admins: the screen counts `GET /users?roleId=<Admin>&active=true`.
- `GET /users/options?active=false` returns only deactivated users (used for the Who filter);
  the activity Who filter is hidden for viewers without users.manage / owners.assign.
